# 本机代码生成与按需视觉

> 后续配置：视觉编码已移到[同一 RTX 3090](neko-same-3090-vision-2026-10-10.md)；代码生成改为[独立低强度思考](neko-game-role-reasoning-2026-10-10.md)，聊天和视觉继续关闭思考。下文保留 10 月 9 日的部署及测量记录。

## 最终配置

聊天、写脚本和理解截图共用 `http://127.0.0.1:18030/v1` 的 `qwen3.8-flash-next-iq3_xxs`，主模型继续使用 RTX 3090，`reasoning_effort=none`，服务上下文上限 262144。三个 profile 字段是用途分工，没有加载三份模型，也没有换成另一个 VLM。

图片编码改用 CPU，8 线程、最多 512 图片 token。实际 `strata-vision.exe` 命令没有 `--gpu`；3080 Ti 不参与该编码路径。桌面和网页渲染仍可能产生显示用 GPU 活动。3090 在一次自主推理期间实测占用 22926/24576 MiB、利用率 100%。同卡编码会与现有模型共享显存；本次采用用户选择的 CPU 方案。

Qwen 的视觉能力之前没有启用：已安装匹配的 encoder/projector，但服务配置缺少 `vision` 块和引擎 `--vision`。Strata 的[安装文档](https://github.com/Niko1221/Strata/blob/main/docs/AI_SETUP.md)也说明 `--yes` 默认关闭图片，需要显式选择视觉方式。本次复用了现有文件，没有重新下载模型。

## 可复现设置

在既有 Strata JSON 保留全部模型参数，只给引擎 `args` 增加 `--vision`，并设置下列块。路径按本机现有安装调整；不要覆盖其他参数或重新初始化用户记忆。

```json
"vision": {
  "exe": "E:/ai-models/Strata-runtime/engine/strata-vision.exe",
  "mmproj": "E:/ai-models/Qwen3.8-Flash-Next-GGUF/mmproj-Qwen3.8-Flash-Next-BF16.gguf",
  "model": "E:/ai-models/Strata-data/models/IQ3_XXS/Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-00001-of-00002.gguf",
  "gpu": false,
  "max_tokens": 512,
  "threads": 8
}
```

重启后检查 `/health`：`loaded=true`、`images=true`、模型名与上下文上限正确。服务只监听本机；局域网访问的是现有现代 viewer，不需要开放模型服务。

Minecraft 运行设置启用 `allow_insecure_coding=true`、`allow_vision=true`、`code_timeout_mins=3`，从禁用清单中移除 `!newAction`、`!lookAround`、`!lookAtPlayer`、`!lookAtPosition`。`profiles/neko-local-trial.json` 明确给三个模型角色配置同一地址和模型；视觉输出上限 384 token，聊天/代码上限各 2048 token。

安装本分支依赖中的 `playwright-core=1.63.0`。Windows 使用现有 Edge，也可用 `NEKO_VISION_BROWSER` 指定浏览器可执行文件。保持 `NEKO_DISABLE_INPROC_VISION=1`、`NEKO_AGENT_SCREENSHOT_INTERVAL_MS=0`：Minecraft 主进程不加载原生 GL，也不定时截图。Neko 本体和 Minecraft 插件按原有生命周期一起运行，高层决策仍归 Neko，原生任务执行器可按需调用新增能力。

## 修复的真实路径

- 原有视觉请求用了错误的 Chat Completions 图片字段；文本格式化还会把图片数组转成 `[object Object]`。现在独立保留 `text`/`image_url` 消息，传递真实图片、取消信号与错误，45 秒请求时限且不自动重试。
- `!lookAround` 不转头、不移动；目标视角命令仍按原语义调整视线。截图复用现代 viewer 的本机捕获租约，短生命周期浏览器拥有 WebGL，25 秒截止并清理浏览器/租约。外部可见 viewer 与局域网访问方式保留。捕获与模型调用均为单次按需调用。
- 方块等结构化事实在截图后、模型请求前固定，避免慢推理结束时读取另一位置的方块。视觉提示只描述地形、危险、结构和通路，不猜 HUD 坐标、背包数量、魔力或权限；这些由游戏数据和真实回执确定。
- 生成器等待模板就绪，正确释放失败请求的单飞标记，并绑定原来的游戏身体。最多 3 次纠错、总预算 180 秒，单次模型请求不超过 45 秒；历史最多 32 条/12000 字符。
- 生成 JavaScript 在可终止的独立 worker 内执行。修复了 lockdown 包装函数递归调用自身的问题；SES 初始化只发生在 worker。默认脚本最长 120 秒、64 次 API 调用、24000 字符，worker 内存有界。生成代码只获得文档列出的 skills/world、只读身体状态、实时背包和私有日志；不提供原始聊天、文件、网络或导入接口。
- 已验证技能调用仍在原 Mineflayer 身体执行，沿用原来的保护和中断检查；自定义技能也受同一可运行目录限制。脚本里的 CPU 死循环不会阻塞 Mineflayer 事件循环；原生可信技能本身的取消能力仍取决于其既有实现。
- 空操作和明确 false 会返回可纠错证据。三轮耗尽也返回明确失败，批次不会把非空错误文字误当成功后继续执行。执行回执证明调用发生，任务完成仍需检查结果。

工具和脚本日志留在内部，实际沟通继续使用已有公聊/私聊工具。没有新增十秒定时视觉或脚本任务，也不强行打断健康动作。

## 验证与实际限度

原生源分支测试 450 项通过；贡献分支完整 `node --test` 自动发现 476 项，全部通过。覆盖无限循环终止、身体更换/中断、调用限额、未授权 API、false 反馈、空操作纠错、请求门控与超时、图片格式、捕获租约清理，以及慢视觉请求的事实时间一致性。Neko 插件/宿主此次未改代码，保留上次 155/195 项回归记录，没有把旧记录当作本次重新执行。

实际本机代码模型在离线假背包/假技能上先用了错误的 `sticks` ID，收到真实查询结果后改为 `stick`，成功调用一次假合成并输出内部日志；这一轮约 5.4 秒。没有借测试向在线游戏注入任务、聊天或技能。

CPU 8 线程、512 图片 token 的最终配置，用已保存的真实游戏截图和当前视觉提示，图片请求耗时 8257 ms。这包含图片编码及同一 Qwen 的视觉推理，不含浏览器截图；此前首次浏览器捕获独立耗时 19198 ms。CPU 6 线程/1024 图片 token 的早期完整截图请求约 20.5 秒。不同设置和一次采样不能视作稳定吞吐基准。

截图验证中模型能识别地下环境，但也出现了矿物误认、坐标和物品数量误读，所以结构化观测优先，不能把画面理解当作权限或物品判断的依据。

部署后恢复 Neko 主分析器、Minecraft 插件和无人值守守护器。独立 55 秒被动观察看到她自行派发制作/放置工作台任务，背包实际变化，任务返回完成，无身体交接失败；随后她自行查询技能并调用服务器勘探能力。观察没有注入这些指令。短窗口不能证明长期无人值守可靠性。

生成脚本会保存审计文件；经验摘要和既有技能发现继续工作。此次没有实现自动技能评测/晋级、自动修改源码或模型权重训练，不能把错误重试称为完整自我进化。
