# Neko 自主运行诊断（2026-10-09）

已确认的问题在 Agent 的信息处理链路。没有修改服务器、服务器权限或其他 Agent，也没有注入诊断任务、公屏聊天或技能施放。

## 已提交并部署的修复

1. **自定义物品身份丢失。** Mineflayer 已提供 1.20.6 的组件名称，但快照解析没有展开其中的 NBT 文本；原生 `!inventory` 只返回基础 ID 和数量。现在快照和背包查询共用名称/说明解析，同时保留命令需要的基础 ID。
2. **决策摘要漏掉关键补给。** 拥挤背包在 400 token 摘要里会完全降为查询链接，700 token 摘要也会漏掉后面的物品。现在独立保留镐及状态、木料、木棍、工作台/熔炉、铁料和自定义物品身份；未收到或已截断的数量不会被当成零，省略项明确计数。
3. **失败恢复依据不足。** 旧实现只保留最后一次结果，优先完成通知还可能先于被动状态到达。现在保留最多 8 条匹配任务的终态；新会话清空旧记录，外来、重复和过期回执不污染历史。完成通知优先预留最新物品状态和失败依据。
4. **已有技能不够显眼，执行提示重复。** `!goToSurface`、`!pillarUp`、`!craftRecipe`、`!serverQuery`、`!serverCommand` 本来就有，当前部署也没有禁用。命令说明前面新增按实际可用性过滤的恢复入口；本地执行档案删除重复规则，修正字面换行和引号转义。

## 已修复的本体传输问题

实机消息总线抓取和离线重放确认：Minecraft 插件发送的 **840 token** 通知，经过 `plugin/server/messaging/proactive_bridge.py` 的通用结果解析后只剩 **200 token**，当前背包资源和失败依据尚未到达模型就被截掉。后面的 1,000 token 回调上限无法补回已经丢失的信息。

用户确认后，已将独立补丁纳入 `integrations/project-neko/host-patches/` 并部署：仅对 Minecraft 的 v2 通知使用现有的 1,000 token 回调上限；其他插件、旧格式和解析行为保留。重启本体后，被动抓取实际模型输入，确认完整的 759 和 858 token 通知到达模型，保留了石镐耐久、资源、法杖和保护信息。

N.E.K.O. 的 `CONTEXT.md` 要求平台层修改先确认；本次用户已明确批准这项消息桥修改。只重启 Minecraft 插件不能加载本体消息桥修复，配套说明已写明正确生命周期。

## 无人值守的后续阻碍

5. **采矿结果没有回传。** 实际成功获得 18 个粗铜，但技能只向文件记录结果，执行模型只看到寻路/丢弃日志；随后多次满包、零增量仍反复采矿。现在动作返回实际增量、库存、完成/部分完成/无进展/中断及背包阻碍。
6. **其他实体的氧气污染自身状态。** 已安装 Mineflayer 的元数据处理会把附近实体氧气写入自己的氧气值。实际依赖离线重放可复现满氧被附近实体改成 0；这会触发生存判断并重置心跳退避。现在现代协议从自身实体读氧气，真实低氧告警继续生效。调度重放中，稳定状态 90 秒只在第 10/40 秒唤醒；错误氧气抖动则每 10 秒唤醒。没有通过忽略真实氧气变化来掩盖问题。
7. **满包合成丢产物、假报成功。** Mineflayer 在背包无空位时可能静默丢弃合成产物并返回成功。现在合成前保守预留空间，不自动丢弃服务器物品；现代协议复用现有全量背包确认，只有实际收到预期增量才报告成功。旧版事务确认路径保留。背包空位也传入 Neko 的精简决策上下文。
8. **规划错误要求橡木。** 通用配方曾固定展开成橡木，持有云杉木仍显示缺橡木。现在规划与实际合成共用通用木材范围，按真实木材/木板和递归余料分配；橡木船等树种专属配方不误用云杉。

## 从观察到行动的补充修复

9. **观察后只有计划，没有动作。** 实际模型输入已包含完整资源，工具也未被拒绝或耗尽预算，但模型查询 `minecraft_observe` 后直接结束回复。精简后的任务说明明确区分最新用户任务与持续自主授权；观察、完成回执和游戏文本本身不产生新授权。插件在观察结果末尾附加自己的 `decision` 与 `llm_instruction`，保留当前连接、状态新鲜度、待执行任务和身体活动信息。只有已配置无人值守且身体明确空闲时，才条件性提示用 `minecraft_task` 执行一个短目标；最新停止/暂停指令优先，忙碌、停止、断线或未知状态不提示新动作。不确定配方应先验证，不能把“台阶拆回木板”当成已知能力。
10. **散文里的命令名称会停止目标。** 执行模型解释 `!cannotComplete`、`!craftRecipe` 等名称时，旧解析器会把缺参的提及当作调用；参数校验前的目标状态更新还会停掉 self-prompt。原生补丁区分实际调用与引用/思考文本，并把目标状态更新移到完整参数校验后。生命周期命令现在独占一行，命令文档及继承的停止、设定目标、完成示例同步调整；回归测试加载实际提示继承链，避免旧示例与新语法冲突。
11. **树冠中的瞬时“活埋”抢断砍树。** 实际采集原木时，机动性检测两次短暂进入 ENTOMBED，取消 `getWood` 后去挖树叶，两秒左右又恢复 FREE。原生补丁只在指令任务正在执行、当前或最近 3 秒内有同一动作代次的真实树木挖掘目标、周围阻挡全部是树叶/原木等树木方块时，给树冠处理最多 8 秒。这个上限覆盖一次徒手挖原木与拾取间隙；持续卡住仍可救援。致命状态、SEALED、石头和未知地形保留原脱困路径。

本节中的插件决策提示已在实际调用链观察；命令解析与树冠让位属于本轮原生补丁。最终部署和导出版本以清单中的源提交为准。

后续实机验证还复现并修复了三个恢复阻碍，不能用先前的成功采集掩盖：模型把位置参数写成 `!mineOres({"ore":"coal"})`，拒绝执行后缺少纠错反馈。现在这类明确的独立调用仍不执行，但内部历史会收到参数定义及验证过的 `!mineOres("coal")` 示例，由模型自行修正，不刷公屏。软 MAROONED 曾禁止任务寻路，而当前任务又禁止对应行军运行，形成循环等待；现在目标导航、坐标导航、矿石隧道和采矿共用控制权判断，被冻结的行军不再占用任务导航，真正持有身体的行军及危险救援保留。矿道入口也不再在有效外部任务期间擅自折返床锚；独立运行及过期租约保留旧策略。路线、视线、挖掘安全和服务器保护检查均保留。

最后一轮还确认了等待预算冲突：她已补出石镐，走出约 100 格并种下云杉树苗，却调用 `!standby(300)`，超过任务剩余时限，19:06:59 实际以 deadline 结束。现在待命动作在取得身体前检查当前任务的滚动/墙钟截止时间，并预留 30 秒用于后续判断/反馈；这是一项保守策略，不是模型响应时限保证。无法容纳的等待会返回剩余时间和短步骤建议，不开始计时、不假报树已长成，也不自动结束任务。独立运行的正常待命、原有 1–1,200 秒参数范围、停止和危险处理保留。
