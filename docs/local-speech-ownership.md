# 本地慢语音的轮次归属与重复播报排查

2026-10-11，Neko 源提交 `30fbea9463f71f3c4d1d26b98eda3d9f174820c4`（包含 `b390fc7e`、`75a14552`），由 `integrations/project-neko/host-patches/0020–0022` 保存为配套补丁。主要针对本机 VoxCPM2 延迟合成与主脑文本提前结束的组合，不改游戏模型、推理槽位或上下文策略。

## 实际证据与归因

用户报告完全相同的播报反复出现。修改前的总线元数据样本含 63 条主动回复，其中一个完整回复哈希出现两次；不能据此断言所有重复都来自播放器。17:00 后统计到 25 次播放结束看门狗；部分自然回复从生成结束到 TTS 完成需 35–71 秒，个别超过 100 秒。语音服务处于 active，未重启。这些是本次观测，不是固定性能指标。

失败回归验证了：

1. 本地 worker 发送裸 PCM。旧轮 A 合成未结束时主脑已开始 B，宿主会把 A 的音频标成 B，但完成信号仍是 A。
2. 旧 A 音频可以错误地确认 B 的故障回退账本，改变未播部分的重放范围。
3. 新文本轮清理前端映射，旧轮音频结束时不能正常回传结束信号。
4. 超时从首次播放开始计时，即使长句刚送出真实音频也可能提前放行下一条主动回复。
5. 初次部署后自然运行仍有一次在分句间隙发送结束、下一句重新开始；文本轮重置会清空旧 started 标记，迟到文本完成还可能覆盖新轮完成状态。再增加两个排序回归复现了这两个边界。
6. 第二次自然验证仍有提前结束，直接触发点是原有缺少完成信号的兜底只有 700 毫秒；它无法覆盖实际超过十秒的本地分句合成间隔。新增回归在 700 毫秒空档明确失败。

这证明了归属和完成处理的缺陷，尚不能单独证明用户听到的每次重复都是同一 PCM 被播放两次。

## 回归报告 / Regression Report

改动及必要性：仅本地 VoxCPM2 选择带源 speech ID 的 worker 输出；宿主音频头携带对应 turn ID；回退账本只确认自己的音频。前端将音频流归属与当前文本轮分开，旧音频收尾不清理新文本，重复结束通知只生效一次。取消与 epoch 变更仍作废旧代际。

长本地播报的现有 45 秒兜底改为参考最近实际音频送达；没有新音频仍会超时，其他 provider 仍使用原有超时。没有添加语音文本去重或静音，不禁止合理的同句回答，不新增模型调用。

0021 补充用真实活动音频判断是否仍需等待流结束；迟到 A 文本完成只尝试收尾 A 的音频，保留 B 的文本与完成状态。初次自然观察暴露的问题没有被单元通过或最终回执掩盖，保留在本地第一轮部署证据中。

0022 由本地 worker 的音频头明确声明 `audio_done_expected=true`，前端仅对该类流使用 45 秒有界完成等待，收到新音频重设等待；整轮完成信号到达仍立即收尾。等待此信号时不走原 700 毫秒或 30 秒粘滞标志兜底。未知 provider 的 700 毫秒策略保留；缺失信号的 45 秒退出也有回归，未关闭取消能力。

诊断只增加轮次 ID、时刻、分句字符数/哈希、音频帧数/字节数/哈希、实际播放开始和结束回执。原始提示、回答、思考、PCM、音色及凭据不写入这批诊断记录。

前后行为：慢 A 与新 B 的模拟请求修复前音频全部归 B，修复后分别归 A/B；两个合法的相同短句均保留且 PCM 不额外复制。旧 A 不再确认 B；新文本开始后旧音频仍能正确结束；长本地播报不会因首次开始时间超过 45 秒而在最近音频送达后立即放行。

潜在回归与覆盖：音频头与二进制配对、取消代际、provider 切换/故障回退、残缺 PCM、同句合法重复、迟到完成、流关闭后续答、其他 provider 的默认流式行为。共享 worker 的 `scoped_audio` 默认关闭，仅本地主力启用。

验证：最终相关 2130 项通过；Ruff、两个 JavaScript 模块的 Node 语法和 `git diff --check` 通过。一个 `test_failed_takeover_with_stale_token_still_unmutes` 日志捕获断言在原 `02c325c2` 的独立归档中同样失败（ERROR 实际输出，但 caplog 未捕获），最终相关集单独排除此项，没有修改无关日志机制。最终补丁数量与文件回放结果见 manifest 和本地 companion-proof.json。
